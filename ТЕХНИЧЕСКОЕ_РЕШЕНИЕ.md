# 4. Backend

## 4.1. Bootstrap (`main.ts`)

Порядок: `helmet` (`crossOriginResourcePolicy: cross-origin` для статики) → `enableCors()` → статика `UPLOAD_DIR` по `/uploads/` → глобальный префикс `api` → `ValidationPipe({ whitelist, transform })` → Swagger на `/api/docs` (bearer) → `listen(PORT ?? 3000)`.

## 4.2. Глобальные механизмы (`app.module.ts`)

- `EventEmitterModule.forRoot()` — доменные события (`achievements.unlocked` и др.) связывают модули без прямых зависимостей (tracks/events → gamification → notifications/posts).
- `ThrottlerModule` + `ThrottlerGuard` как `APP_GUARD` — `RATE_LIMIT_PER_MINUTE` (default 500)/мин.
- `JwtAuthGuard` как `APP_GUARD` — **все эндпоинты аутентифицированы по умолчанию**; исключения помечаются `@Public()` (register/login/refresh/forgot/reset/verify, `/api/health`, `GET /search` — через `OptionalJwtAuthGuard`, чтобы фильтр блокировок работал и для гостей с токеном).
- Гвард проверяет существование и `is_banned` пользователя на каждый запрос.

## 4.3. Аутентификация и аккаунт (`auth`, `users`)

- Пароли — bcrypt(10). Access-токен JWT (7d, `JWT_SECRET`), refresh-токены — таблица `auth_tokens` (типы `refresh/email_verify/password_reset`) с **ротацией** refresh при `POST /auth/refresh`.
- `logout` — отзыв текущего refresh, `logout-all` — всех refresh пользователя.
- Подтверждение email и сброс пароля: токен из `auth_tokens`; письмо шлёт `MailService` — при настроенном SMTP (`MAIL_HOST/USER/PASS`) реальное письмо, иначе лог + `devToken` (только вне production).
- Приватность и предпочтения профиля: `profileVisibility / activityVisibility / geoVisibility` (`public|friends|private`) + `showOnline`; `locale` (`ru` по умолчанию, `en`) — язык интерфейса, хранится на сервере (`users.locale`), возвращается в auth-ответах и `GET/PATCH /users/me` / `GET /users/:id/profile`, валидируется в `UpdateUserDto` (`IsIn(['ru','en'])`). `GET /users/:id/profile` собирает статистику с учётом видимости.
- Роли: `user`, `guide` (в модели, в UI не используется), `moderator`, `admin`; стафф-проверки — `RolesGuard` + `@Roles('admin','moderator')`.

## 4.4. База данных

- Подключение: `DB_HOST/DB_PORT/DB_USERNAME/DB_PASSWORD/DB_DATABASE` (default `sup_fun`); `DB_SYNC=true` включает synchronize, миграции из `dist/migrations` выполняются всегда, кроме `DB_RUN_MIGRATIONS=false`.
- PostGIS: `waterbodies.location` — geography Point SRID 4326 (+пространственный индекс, `synchronize:false`); у треков — линия маршрута (`buildRouteLine`) и точки `track_points`.
- Таблицы (30): `users, auth_tokens, waterbodies, events, event_participants, event_invites, tracks, track_points, point_logs, user_achievements, friend_requests, user_blocks, conversations, conversation_participants, messages, notifications, device_tokens, notification_settings, listings, listing_leads, listing_favorites, listing_reviews, posts, post_likes, post_comments, channels, channel_members, channel_posts, channel_post_likes, channel_post_comments, news, gear_items`.
- Ключевые ограничения уникальности: `users.email`, `channels.slug`, `channel_members(channel_id,user_id)`, `notification_settings(user_id,category)`, `user_achievements(userId,achievementCode)` — идемпотентность достижений.

## 4.5. Доменные модули (ключевые решения)

**waterbodies** — справочник с PostGIS: `GET /waterbodies` (q+пагинация), `nearby` (ST_Distance), создание/редактирование только через `admin` (публичный POST удалён). `latitude/longitude` подкладываются в DTO из geometry.

**events** — заплывы с видимостью (`assertVisible` при чтении), приглашениями (`event_invites`, уведомление `event_invite`), участием со статусами `going/maybe/not_going` и управлением участниками организатором. При создании события автоматически создаётся чат типа `event` (ошибку чата глотаем — чат вспомогательный). При завершении привязанного трека участник авто-помечается завершившим.

**tracks** — загрузка точек пачками (`POST /tracks/:id/points`), `complete` пересчитывает дистанцию (haversine по точкам), среднюю/макс. скорость, набор/сброс высоты, калории; публикуется маршрутом (`publish`, XP 15). Offline/background — зона ответственности будущего мобильного клиента (сервер готов к отложенной загрузке точек). Контроль доступа — `ensureEditable(id, me)`: владелец **или** стафф (`admin`/`moderator`) могут править трек, публиковать его и досылать точки; `GET /tracks/:id` открывает чужой приватный трек стаффу; `DELETE /tracks/:id` — владелец или только `admin`. Все методы сервиса получают объект `AuthUser` (не `userId`), поэтому XP за `track_completed`/`route_published` начисляется `track.userId`, а не инициатору — публикация чужого трека стаффом не «переадресует» баллы. Новые эндпоинты (v0.6): `GET /tracks/:id/points` (возврат точек трека для карты), `PUT /tracks/:id/points` (полная замена точек; сервер пересчитывает дистанцию, скорости, высоту, калории и обновляет `route_line` LineString через `ST_MakeLine`). Web: `GET /tracks/:id/points` используется `TracksPage` (мини-карта) и `TrackDetailPage` (полная карта с полилинией и маркерами старт/финиш); `PUT /tracks/:id/points` используется `TrackEditPage` (редактор маршрута: перетаскивание маркеров, добавление кликом, удаление, сортировка).

**Справочник маршрутов** — `GET /tracks` с фильтрами `scope` (`all` — опубликованные плюс свои черновики, `mine`, `public`), `waterBodyId`, `difficulty`, `minDurationSec`/`maxDurationSec`, `limit`/`offset`; в web это одна страница со списком карточек и панелью фильтров (водоём, сложность, диапазон времени в пути, «только мои»), вкладок нет.

**Ручная правка метаданных.** `UpdateTrackDto` принимает, кроме `name`/`waterBodyId`/`difficulty`, ещё `distanceMeters`, `durationSeconds`, `avgSpeedKph`, `maxSpeedKph`, `elevationGainMeters`, `elevationLossMeters`, `calories` — редактор показывает их полями, плюс кнопка «Пересчитать из точек» (тот же haversine, что и на сервере). `PUT /tracks/:id/points?recalc=false` заменяет геометрию **без** пересчёта статистики, иначе автпересчёт затёр бы ручные значения; `recalc=true` (по умолчанию, поведение мобильного клиента) пересчитывает как раньше. **Порядок точек задаётся `recorded_at`** — и `GET /tracks/:id/points`, и `buildRouteLine` (`ST_MakeLine(... ORDER BY recorded_at)`) сортируют по нему, поэтому редактор при сохранении заново расставляет метки времени строго по позиции точки (границы интервала берутся из исходных точек, чтобы не менять длительность заплыва, шаг не меньше секунды). `replacePoints` пересобирает `route_line` **после** `tracksRepository.save(track)`: сущность загружена до замены точек и содержала старый `route_line`, которым `save()` иначе обнулил бы новый. Координаты проверяются `@Min/@Max` по широте и долготе.

**Карта и React.** Контейнер Leaflet нельзя давать в `className` ничего динамического: при смене значения React перезаписывает атрибут `class` и стирает служебные классы Leaflet (`leaflet-container` и др.), после чего карта визуально исчезает. Рамку/курсор режима правки вешают на родительскую обёртку, у контейнера класс постоянен; карта создаётся один раз (зависимость эффекта — только от флага готовности), а перезагрузка трека после сохранения идёт в `silent`-режиме, чтобы узел карты не размонтировался. Регрессия — `server/scripts/smoke-track-points.js` (`npm run smoke:track-points`, 35 проверок: порядок точек, пересчёт и ручная правка метаданных, `recalc=false`, `route_line` из всех вершин, все фильтры справочника, `null` высота/скорость, 400 на невалидную широту, 403 постороннему, 401 без токена).

**marketplace** — листинги с предмодерацией (`LISTING_AUTO_APPROVE`, по умолчанию true), статусы `draft/moderation/active/completed/sold/removed`, до 6 фото, фильтры `category/city/q/sellerId/sort`, избранное, leads, отзывы 1–5 **только от покупателя принятого лида**, агрегатный рейтинг продавца.

**posts/feed** — лента агрегирует published-треки, scheduled-события, active-листинги; везде SQL-фильтр `NOT IN blocked`. Авто-посты: завершение трека, создание события, разблокировка достижения (`@OnEvent('achievements.unlocked')`).

**channels** — см. §47.12 п.2 ТЗ. Правила доступа в `ChannelsService.assert*`: чтение публичных — всем авторизованным; приватные — участникам и стаффу/владельцу; постинг/комментарии — только участникам; pin/удаление чужого — owner/moderator; смена ролей — только owner; owner не может выйти.

**news** — опубликованные видят все авторизованные, черновики — только staff (`includeDrafts=true`); мутации за `RolesGuard`.

**gear** — CRUD + чтение чужого списка с проверкой видимости профиля владельца.

**reference (страны)** — таблица `countries` (`code` ISO 3166-1 alpha-2 PK, `name_ru`, `name_en`), справочник отдаётся публичным `GET /reference/countries` (сортировка по русскому названию). Источник данных — датасет `mledoze/countries`, из него скриптом `server/scripts/gen-countries.js` сгенерирован TS-модуль `src/modules/reference/data/countries.data.ts` (250 стран): TS, а не JSON, потому что сборка идёт `tsc -p tsconfig.build.json` без копирования ассетов. Заполнение идемпотентно — upsert в `onApplicationBootstrap`, повторный старт сервера не создаёт дублей и не затирает правки. Поле `users.country` — теперь код справочника (`varchar(2)`, по умолчанию `'RU'`); `UsersService.normalizeCountry` приводит регистр к верхнему и отдаёт 400 на неизвестный код, поэтому в профиле страна выбирается только из справочника.

**Заплыв через маршрут** — у события появился `track_id` (`Event.trackId` → `ManyToOne('Track')`, строковое имя сущности из-за циклического импорта track↔event, `onDelete: 'SET NULL'`). `EventsService.applyTrack` подтягивает из маршрута водоём, длительность и дистанцию — в заплыве они только для чтения. `findAll/findById` отдают `relations: { track: true, waterBody: true }`, чтобы список и карточка рисовали название маршрута без N+1. Фильтры списка: `?trackId=` и `?date=ГГГГ-ММ-ДД` (сутки считаются в локальной таймзоне сервера, `Invalid date` → 400).

**reviews (отзывы)** — единая таблица на отзывы о маршрутах и заплывах: полиморфная связь `target_type` (`track`/`event`) + `target_id` без FK, `rating` 1–5, `photos` (массив URL из `uploads`), `text`. Уникальность `(target_type, target_id, author_id)` — один отзыв на пользователя, повторная отправка обновляет существующий. Существование цели проверяется в сервисе (404), правка/удаление — только автору. Эндпоинты: `GET /reviews?targetType=&targetId=`, `GET /reviews/summary` (`count`/`avgRating`), `POST /reviews`, `PATCH /reviews/:id`, `DELETE /reviews/:id`. Web — компонент `ReviewsSection` (звёзды, текст, до 6 фото через `ImageUploader`) в `TrackDetailPage` и `EventDetailPage`.

**Треки участников заплыва и приём точек с мобильного** — под заплывом понимаются обычные `tracks` с заполненным `event_id`; отдельные таблицы не заводятся. Контроллер `EventTracksController` (`tracks/event-tracks.controller.ts`) даёт мобильному клиенту три шага: `POST /events/:id/tracks` — старт записи (идемпотентен: до финиша возвращает тот же трек, водоём наследуется с маршрута заплыва), `POST /events/:id/tracks/:trackId/points` — пачка точек, `POST /events/:id/tracks/:trackId/finish` — финиш (тот же `complete`: пересчёт статистики, `route_line`, XP, авто-отметка участия). Идемпотентность пакетов держится на колонке `track_points.seq` (порядковый номер точки на клиенте) с частичным уникальным индексом `(track_id, seq) WHERE seq IS NOT NULL`: известный `seq` отбрасывается на уровне сервиса, гонка двух пакетов гасится `orIgnore()` (`ON CONFLICT DO NOTHING`), ответ — `{added, skipped, total}`. После `ended_at` точки не принимаются (403). Чтение (`GET /events/:id/tracks`, `GET /events/:id/tracks/:trackId/points`) закрыто всем, кроме участников заплыва/организатора (`assertEventParticipant`). Web — `EventTracks` на странице заплыва: список участников со статистикой и карта со всеми линиями разными цветами.

**Регрессия новых модулей** — `server/scripts/smoke-new-features.js` (`npm run smoke:new`, 51 проверка: справочник стран и валидация кода в профиле, правила уровней, наследование водоёма/длительности/дистанции из маршрута, фильтр по дате, отзывы включая 403 на чужой отзыв и 404 на несуществующую цель, старт/пакеты/повторы/финиш трека и закрытие доступа после финиша).

## 4.6. Геймификация (`gamification`) и рейтинг (`ratings`)

- Начисления (всё сервером, журнал `point_logs` + инкремент `users.xp`): `track_completed` 10, `distance_bonus = floor(км/5)*5` (при ≥5 км), `group_swim` 10 (событие с ≥2 «иду»), `route_published` 15, `event_created` 20, достижение — его XP.
- Уровень: `need₁ = 200`, `needₙ₊₁ = round(needₙ × 1.4)`; ответ `/gamification/me` — `{level, xp, currentLevelXp, nextLevelXp, progress}`. Публичный `GET /gamification/rules` отдаёт то же самое справочно: формулу, пороги первых 12 уровней, таблицу начислений и список достижений — на web-странице `/gamification`. Пороги считаются функцией `levelThresholds()`, той же, что и `levelForXp`, поэтому страница не расходится с реальным расчётом.
- Достижения 7 шт. (см. ТЗ §18.2), проверяются в `track_completed` (6) и `event_created` (`first_organizer`); разблокировка идемпотентна; эмит `achievements.unlocked`.
- **Ratings:** один SQL-запрос с параметризованным `where` по scope; `season` — подзапрос суммы `point_logs` за текущий UTC-год; из выдачи исключаются забаненные и пользователи, скрывшиеся (blocks); уровень считается той же функцией, что и в gamification.

## 4.7. Realtime-чат (`messages`, `chat.gateway.ts`)

Namespace `/chat`, аутентификация сокета JWT-handshake. Комнаты: `presence`, `user:{id}` (личная доставка, в т.ч. `notify:new`), `conv:{id}`. События клиента: `conversation:join/leave`, `chat:send`, `chat:delivered`, `chat:read`, `chat:typing`, `presence:list`; сервера: `chat:new`, `chat:status`, `chat:typing`, `presence:change`, `notify:new`.

Типы чатов `direct/group/event/deal`; типы сообщений `text/photo/location` + `nonce`/`replyToId` (задел E2E). Сервер валидирует координаты для `location`; web-UI пока отправляет только `text`.

## 4.8. Уведомления и push (`notifications`)

Конвейер `notify(userId, type, title, body, data)`:

1. `type → category` (7 категорий: events, messages, achievements, community, news, marketplace, weather);
2. читается `notification_settings` (default in-app+push включены) → при `inApp=false` уведомление не создаётся;
3. in-app: запись `notifications` + push-в-сокет `notify:new`;
4. push: только при `push=true` и настроенном FCM (`FCM_PROJECT_ID/FCM_CLIENT_EMAIL/FCM_PRIVATE_KEY`) — токен OAuth кэшируется до истечения, отправка на все `device_tokens` пользователя (HTTP v1, `messages:send`), ошибки логируются без падения.

Устройства: `POST /devices/register`, `DELETE /devices/:token`. Настройки: `GET /notifications/settings`, `PATCH /notifications/settings/:category`.

## 4.9. Загрузка файлов (`uploads`)

Multer disk storage → `UPLOAD_DIR` (default `server/uploads`), имя `randomUUID.ext`, лимит `UPLOAD_MAX_MB` (5), MIME `jpeg/png/webp/gif/avif`. `POST /uploads/image` → `{url}`, `POST /uploads/images` (до 10) → `{urls}`. Отдача — экспресс-статика `/uploads/*`. Применение: аватар, фото объявлений (≤6), фото событий, обложки новостей, фото каналов.

## 4.10. Админ-модуль

`stats` (счётчики), пользователи (роль/бан/разбан), модерация листингов/треков (статусы), события (статус + редактирование + удаление), водоёмы (полный CRUD + `active`). Доступ — `RolesGuard(admin/moderator)` + `StaffGate` в web.

Разделение прав: статусы/модерация доступны `admin` и `moderator`, деструктивные операции (`users/:id/role`, ban, `DELETE /admin/events/:id`, `DELETE /admin/waterbodies/:id`) — только `admin`. Чужие маршруты правятся через пользовательский эндпоинт `PATCH /tracks/:id` (права проверяет `TracksService.ensureEditable`), удаляются — `DELETE /tracks/:id` (владелец или `admin`); отдельного `/admin/tracks` нет — управление маршрутами consolidated в `/tracks` с кнопкой «Редактировать» для автора/стаффа. В `/admin` остались только `users`, `listings`, `events`, `waterbodies`.

# 5. Web-клиент

## 5.1. Сессия и axios (`lib/api.ts`)

- Хранилище: `localStorage` (`sf_token`, `sf_refresh`, `sf_user`).

Один сокет к `/chat` с JWT; хук `useSocketEvent(event, handler)` для подписок; Layout слушает `notify:new` (счётчик уведомлений), чаты — `chat:new/status/typing`.

## 5.4. Карта водоёма (`WaterbodyMap`)

Без ключей и платных провайдеров: 1) Nominatim `search` по имени/региону → osm_type/osm_id; 2) Overpass (два зеркала с фолбэком) → геометрия way/relation; 3) Leaflet рисует контур (тип water/lake/bay/sea/river/…) поверх OSM-тайлов с авто-fitBounds; состояния loading/not-found/error в UI. Это элементная карта карточки водоёма; полноэкранного раздела «Карта» (ТЗ §8) пока нет.

|---|---|---|

Корней проекта — не npm-workspace: `package.json` лежат отдельно в `server/` и `web/`, а в корне добавлен тонкий `package.json` с агрегирующими скриптами (`dev`, `dev:server`, `dev:web`, `build`, `build:server`, `build:web`, `start:server`, `setup`, `smoke:tracks-staff`, `smoke:track-points`), которые вызывают `npm --prefix <пакет> run …`. `npm run dev` исполняет `scripts/dev.js` — runner без сторонних зависимостей: параллельно запускает `server` (`start:watch`) и `web` (`vite`), добавляет префиксы `[server]`/`[web]` к строкам вывода, прокидывает `PORT` и `VITE_API_PROXY` (прокси vite следует за портом backend), останавливает оба процесса при падении одного из них или по Ctrl+C. Порты переопределяются `PORT` / `WEB_PORT` (в PowerShell: `$env:PORT=3100; npm run dev`), скрипт backend — `SERVER_DEV`.

Переменные backend (`.env`): `PORT`, `NODE_ENV`, `FRONTEND_URL`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `DB_HOST/PORT/USERNAME/PASSWORD/DATABASE`, `DB_SYNC`, `DB_RUN_MIGRATIONS`, `DB_LOGGING`, `RATE_LIMIT_PER_MINUTE`, `UPLOAD_DIR`, `UPLOAD_MAX_MB`, `LISTING_AUTO_APPROVE`, `MAIL_HOST/PORT/SECURE/USER/PASS/FROM`, `FCM_PROJECT_ID/FCM_CLIENT_EMAIL/FCM_PRIVATE_KEY`.

# 7. Безопасность (сводно)

1. Default-deny: JWT обязателен глобально, публичные точки перечислимаями `@Public()`.
2. Проверка `is_banned` на каждый запрос; ролевые гейты на стафф-эндпоинтах.
3. Refresh-ротация + отзыв; bcrypt-хэши не отдаются (`select: false`).
4. `ValidationPipe(whitelist)` против mass-assignment; DTO на каждое тело запроса.
5. Rate limiting глобальный; Swagger скрыт за тем же префиксом (в prod требует закрытия).
6. Загрузка файлов: белый список MIME + лимит размера + случайные имена; контент **не** антискемпится (долг).
7. Приватность: видимости профиля/активности/гео, блокировки применяются в feed/posts/search/leaderboard; в публичных ответах пока лишние поля сущностей (долг, ТЗ §47.10 п.1).
8. Права на чужие треки (`TracksService.isStaff`) и аналогичные внутри-модульные проверки берут роль из access-токена (`AuthUser.role`), поэтому смена роли пользователю применяется после перевыпуска токена (пере-логин/refresh), а не мгновенно.

# 8. Известные ограничения (as-built)

Полный список — ТЗ §47.10. Ключевые для архитектуры:

- Нет погодного провайдера и полноэкранного раздела «Карта»; offline/background tracking — зона мобильного клиента.
- E2E-шифрование — только задел (`nonce`); пайплайн чата готов к `photo/location`, UI — нет.
- Push работает только при настроенных FCM-креденшлах; APNs-провайдер отсутствует.
- XP не пересчитывается из журнала; сезонного сброса и наград за сезон нет.
- Новости без категорий/комментариев; уведомления категории «Новости» не генерируются.
- Лидерборд: `me` возвращается только если пользователь попал в топ `limit`.

# 9. План развития решения (следующие шаги)

1. Контракты ответов (DTO-серализация) вместо отдачи сущностей целиком.
2. Провайдер погоды (абстракция + Open-Meteo как кандидат) → блоки §10, §11 ТЗ и категория weather.
3. Раздел «Карта»: общий Leaflet-слой с маркерами waterbodies/events/tracks (данные уже есть в API).
4. Чат: photo/location в UI (сервер готов), затем E2E (libsodium, ключи в `auth_tokens`-подобной таблице).
5. Мобильный клиент: offline-очередь точек трека (эндпоинты пакетной загрузки готовы), push-токены (устройства уже регистрируются).
6. Модерация загрузок (антивирус/NSFW-очередка) и медиан-хранилище вместо локального диска.
