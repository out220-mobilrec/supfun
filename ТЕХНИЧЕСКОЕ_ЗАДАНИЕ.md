# 2. Принципы продукта

## 2.1. Главная идея

SUP FUN — социальное приложение для SUP-сообщества, объединяющее:

1. заплывы;
2. GPS-трекинг;
3. карту водоёмов и маршрутов;
4. социальное взаимодействие;
5. достижения и челленджи;
6. новости;
7. маркетплейс оборудования;
8. безопасность на воде.

## 2.2. Приоритет UX

Приложение должно быть:

- простым вне воды;
- максимально простым на воде;
- визуально ориентированным;
- быстрым;
- пригодным для использования одной рукой;
- пригодным для использования в перчатках;
- устойчивым при плохой сети;
- безопасным с точки зрения работы с геоданными.

## 2.3. Главный UX-принцип

Пользователь должен иметь возможность начать заплыв максимум за несколько действий после открытия приложения.

Основной CTA:

**НАЧАТЬ ЗАПЛЫВ**

Дополнительные быстрые действия:

- Создать заплыв;
- Найти компанию;
- Найти маршрут;
- Посмотреть карту;
- Купить / продать оборудование.

## 14.4. Модерация маршрутов стаффом

Модератор и администратор имеют право редактировать маршруты всех пользователей, включая приватные:

- просмотр карточки чужого приватного маршрута;
- изменение названия, водоёма и сложности (`PATCH /tracks/:id`);
- публикация и снятие с публикации (публикация из админ-панели — через статус маршрута);

Удаление чужого маршрута — только администратор (модератор получает `403`). Обычные пользователи сохраняют полный контроль над собственными маршрутами.

# 18. Геймификация

## 18.1. Экран уровня

Показывает:

**Уровень 18**

560 / 1000 XP

Прогресс-бар.

Следующий уровень:

**Профи**

### Формула уровня (реализовано, v0.5)

Уровень — чисто производная величина от суммарного XP пользователя
(`users.xp`), отдельного поля «уровень» в базе нет и пересчитывать ничего не нужно.

Базовые константы (`server/src/modules/gamification/gamification.service.ts`):

| Константа | Значение | Смысл |
|---|---|---|
| `LEVEL_BASE_XP` | 200 | XP, нужный для перехода с 1-го уровня на 2-й |
| `LEVEL_GROWTH` | 1.4 | во сколько раз каждый следующий порог больше предыдущего |

Алгоритм (`computeLevel(xp)`):

```text
level  = 1
need   = 200                       // need(n) — XP «на уровне» n, от порога к порогу
while xp_remaining >= need:
    xp_remaining -= need
    level        += 1
    need          = round(need * 1.4)

currentLevelXp = xp_remaining      // прогресс на текущем уровне
nextLevelXp    = need              // сколько нужно до следующего уровня
progress       = currentLevelXp / nextLevelXp
```

Суммарный XP для входа на уровень `L`: `total(L) = Σ need(i)` для `i = 1..L-1`.

Пороги (первые уровни):

| Уровень | XP «на уровне» | XP всего |
|---|---|---|
| 1 | — | 0 |
| 2 | 200 | 200 |
| 3 | 280 | 480 |
| 4 | 392 | 872 |
| 5 | 549 | 1 421 |
| 6 | 769 | 2 190 |
| 7 | 1 077 | 3 267 |
| 8 | 1 508 | 4 775 |
| 9 | 2 111 | 6 886 |

|---|---|---|
| Завершён заплыв (трек) | `track_completed` | 10 |
| Опубликован маршрут | `route_published` | 15 |
| Создан заплыв-событие | `event_created` | 20 |
| Заплыв в составе события | `group_swim` | 10 |
| Бонус за дистанцию | `distance_bonus` | 5 × floor(км / 5) |
| Открытое достижение | `achievement` | по таблице §18.2 |

Все начисления пишутся в журнал `point_logs`, суммарный XP хранится в `users.xp`.

Эндпоинты:

- `GET /gamification/me` — уровень, XP, прогресс текущего пользователя;
- `GET /gamification/points` — журнал начислений;
- `GET /gamification/achievements` — каталог достижений со статусом «открыто/нет»;
- `GET /gamification/rules` — публичное описание формулы, порогов, начислений и
  достижений (для справочных экранов клиента).

Веб-страница справки: **`/gamification`** — формула, таблица порогов с отметкой
текущего уровня, таблица начислений XP, каталог достижений с иконками и
расшифровка значков в профиле.

# 19. Баллы

Экран журнала:

Дата | Действие | Баллы

Примеры:

- Заплыв +10;
- 5 км +5;
- Групповой заплыв +10;
- Новый маршрут +15;
- Организация события +20;
- Серия заплывов +25.

**Реализованные начисления (v0.4)** — источник: `server/src/modules/gamification/gamification.service.ts`:

| Действие (`action`) | Баллы (XP) | Условие |
|---|---|---|
| `track_completed` | 10 | завершение трека |
| `distance_bonus` | `floor(км / 5) × 5` | трек ≥ 5 км (начисляется за каждый трек) |
| `group_swim` | 10 | трек привязан к событию с ≥ 2 участниками «иду» |
| `route_published` | 15 | публикация маршрута с дистанцией > 0 |
| `event_created` | 20 | создание заплыва |
| `achievement` | XP достижения (20–150) | разблокировка достижения |

Уровень считается от XP: порог 1-го уровня — 200 XP, каждый следующий — `round(предыдущий × 1.4)`. Пример «+48 баллов» на экране завершения складывается из `track_completed` и `distance_bonus`.

Все расчёты выполняются сервером.

Клиент только отображает результат.

# 47. Фактическая реализация (as-built, v0.5)

Раздел фиксирует, что уже реализовано в коде проекта SUP FUN, и служит источником истины для сверки с §1–46. Технические детали (архитектура, модели, конвейеры, запуск) — в **ТЕХНИЧЕСКОЕ_РЕШЕНИЕ.md**.

## 47.1. Общая архитектура

- **Backend:** NestJS + TypeORM + PostgreSQL + PostGIS. Каталог `server/`. REST API с глобальным префиксом `/api`, OpenAPI/Swagger на `/api/docs`. WebSocket-чат — `socket.io`, namespace `/chat`. Загрузка файлов — `multer`, отдача статики `/uploads/`.
- **Web-клиент** (пользовательский SPA + админ-панель): React 18 + Vite + TypeScript + React Router v6 + axios + socket.io-client + Tailwind CSS. Каталог `web/`.
- **Мобильный клиент:** Flutter — собран визуальный прототип (`SUP_FUN_Flutter_v0.1_VISUAL_FULL.zip`); рабочим приложением не является.
- **БД:** `sup_fun`, PostGIS используется для координат/линий водоёмов и треков. Схема: `DB_SYNC=true` (авто-синхронизация по сущностям) и/или TypeORM-миграции из `dist/migrations` (`migrationsRun`, отключается `DB_RUN_MIGRATIONS=false`; есть миграция `AuthSecurityHardening`).
- **Доступ:** JWT обязателен глобально (`JwtAuthGuard` как `APP_GUARD`), публичные точки открываются декоратором `@Public()` (`/auth/*`, `/api/health`, `GET /search` — опциональная JWT).

## 47.6. Геймификация — точные правила (as-built)

Источник: `server/src/modules/gamification/gamification.service.ts`; триггеры — `events.service.ts` и `tracks.service.ts`.

**Начисление баллов.** Все начисления записываются в `point_logs` и инкрементируют `users.xp`.

| Действие | XP | Условие |
|---|---|---|
| `track_completed` | 10 | завершение трека (`POST /tracks/:id/complete`) |
| `distance_bonus` | `Math.floor(distanceKm / 5) * 5` | при завершении трека, если `distanceKm ≥ 5` |
| `group_swim` | 10 | трек привязан к событию, где ≥ 2 участника в статусе «иду» |
| `route_published` | 15 | `POST /tracks/:id/publish` при `distanceMeters > 0` |
| `event_created` | 20 | создание заплыва |
| `achievement` | равно XP достижения | разблокировка достижения |

**Уровни** (`computeLevel`): `level = 1`, `need = 200`; пока `xp ≥ need`: `xp -= need`, `level += 1`, `need = round(need × 1.4)`. `GET /gamification/me` возвращает `{ level, xp, currentLevelXp, nextLevelXp, progress }`.

**Достижения** (`ACHIEVEMENTS`): проверяются при `track_completed` (первые четыре) и `event_created` (`first_organizer`); разблокировка идемпотентна (уникальность `userId + achievementCode`), XP достижения начисляется в `point_logs` с `action = 'achievement'`.

| Код | Название | Условие | XP |
|---|---|---|---|
| `first_swim` | Первый заплыв | ≥ 1 завершённый трек (`ended_at` задан, дистанция > 0) | 25 |
| `distance_10` | 10 км на воде | суммарная дистанция ≥ 10 км | 50 |
| `distance_100` | 100 км на воде | суммарная дистанция ≥ 100 км | 150 |
| `night_swim` | Ночной заплыв | старт трека в 22:00–05:00 | 30 |
| `first_organizer` | Организатор | создан ≥ 1 заплыв | 20 |
| `social` (v0.5) | Социальный | завершён трек, привязанный к событию с ≥ 3 участниками «иду» | 50 |
| `streak_3` (v0.5) | Серия заплывов | завершённые треки 3 дня подряд (по датам `ended_at`) | 25 |

**API:** `GET /gamification/me`, `GET /gamification/points`, `GET /gamification/achievements`; лидерборд — отдельный модуль `GET /ratings/leaderboard` (§47.12 п.1). Разблокировка публикует событие `achievements.unlocked` → уведомление пользователя и авто-пост в ленте.

**Известные ограничения:**
- `night_swim` определяется по UTC-часу старта трека, а не по локальному часовому поясу — для регионов с ненулевым смещением результат может быть неверным.
- XP хранится инкрементально: удаление/отмена действий баллы не откатывает.
- Проверка достижений вызывается только из двух точек (`track_completed`, `event_created`); достижение «1000 км» отсутствует в каталоге.
- `streak_3` считается по календарным датам завершения треков без учёта часовых поясов пользователя.

- Используется для: аватара профиля, фотографий объявлений (до 6), фотографий заплывов (`Event.photos`, до 6).

**Реализовано:** регистрация и вход по email, подтверждение email и восстановление пароля, профиль с настройками приватности, водоёмы (сущность + nearby + контур на OSM-карточке), одиночные и групповые заплывы (видимость, приглашения, управление участниками, авто-создание чата события), запись GPS-трека, результат заплыва, базовые баллы, достижения (6 из 7 каталога §18.2: все, кроме «1000 км»), публикации с лайками/комментариями/шерингом, личные сообщения и чат события (текст, без E2E), центр уведомлений + FCM + покатегорийные настройки, маркетплейс (объявления, лиды, избранное, отзывы и рейтинг продавца), друзья и блокировки, публичные маршруты, глобальный поиск, расширенный профиль, публичные каналы, новости, снаряжение, лидерборд (друзья/город/регион/страна/сезон), админ-панель.

## 47.10. Технический долг

1. Публичные ответы отдают полную сущность продавца/организатора (включая лишние поля) — ограничить контракт ответа.
2. `night_swim` использует UTC вместо локального времени; `streak_3` — даты `ended_at` без часового пояса.
3. XP не пересчитывается из журнала; лидерборд «за сезон» считается суммой `point_logs` за текущий год без сброса/наград.
4. Чат: заделы `nonce`/`type = photo/location` реализованы на сервере, но не задействованы в web-UI.
5. Upload-файлы не проходят модерацию/очистку.
6. Погода, полноэкранный раздел «Карта», offline — крупные незакрытые блоки MVP/V2.
7. `GET /search` не включает новости и каналы; `/feed` не включает записи каналов.
8. Авто-посты создаются асинхронно (`@OnEvent`), возможна кратковременная задержка появления в ленте.
9. Уведомления категории «Новости»: тип `news` и настройка категории есть, но генерация уведомлений о публикациях не подключена.
10. Новости: нет категорий и комментариев (§36 п.58, п.60 web-реализация — только лента и статья).
11. Снаряжение не связано с заплывами/треками (§17).
12. Лидерборд: позиция `me` возвращается только если пользователь попал в топ `limit`.
13. Роль стаффа берётся из access-токена, поэтому изменение роли пользователю применяется только после перевыпуска токена (пере-логин/refresh), а не мгновенно.

## 47.11. Журнал доработок (v0.4, блоки 1–6)

Пофазно закрыты следующие блоки; каждый проверен runtime smoke-тестом.

1. **Безопасность/корректность.** Убран публичный `POST /waterbodies`; пагинация водоёмов; видимость событий с `assertVisible`; приглашения (`event_invites`) и enforcement доступа; `POST /events/:id/invites`; уведомление `event_invite`.

3. **Приватность/соцграф.** Поля видимости профиля/активности/геолокации; модуль `blocks` (блокировки, скрытие, разрыв заявок); `GET /users/:id/profile` со статистикой; web-настройки приватности и переписанный публичный профиль.
4. **События: управление участниками.** `PATCH/DELETE /events/:id/participants/:userId`, фильтр `?status=`, правила (организатор/участник/полнота); web-управление в карточке заплыва.
5. **Маркетплейс.** Предмодерация (`LISTING_AUTO_APPROVE`, статусы `draft/moderation/sold`), избранное, отзывы `1–5` только после принятой сделки, рейтинг продавца, фильтры `city/sellerId/sort`; web-фильтры, избранное/отзывы в карточке, рейтинг в профиле.
6. **Социальная лента.** Модуль `posts`: CRUD, лайки, комментарии, шеринг, приватность и фильтрация блокировок; авто-посты при завершении трека, создании события и разблокировке достижения; `/feed` защищён JWT и учитывает блокировки; web-компонент `PostList` (композер, лайки, комментарии, шеринг) в ленте и профиле.

## 47.12. Журнал доработок (v0.5)

Подтверждено аудитом кода (backend `server/src/modules`, web `web/src`); закрывает ранее нереализованные пункты ТЗ.

1. **Рейтинг/лидерборд (§18.4).** Модуль `ratings`: `GET /ratings/leaderboard?scope=friends|city|region|country|all|season&limit≤100`. Скор — `users.xp` (для `season` — сумма `point_logs` за текущий год). Сcope-фильтры по `city/region/country` пользователя; исключаются забаненные и те, кто заблокировал смотрящего; уровень считается из XP по формуле §19. Web: страница `/rating` с переключателями scope и подсветкой своей позиции.
2. **Публичные каналы (§21).** Модуль `channels`: таблицы `channels / channel_members / channel_posts / channel_post_likes / channel_post_comments`; публичные и приватные каналы (уникальный slug); роли `member / moderator / owner` (смена роли — только владельцем); публиковать и комментировать могут только участники; закрепление и удаление чужих записей — владельцу и модераторам. Web: `/channels` (список, создание) и `/channels/:id` (лента записей, лайки, комментарии, pin, состав участников).
3. **Снаряжение (§17).** Модуль `gear`: `gear_items` (категории `board/paddle/wetsuit/vest/leash/pump/drybag/other`, бренд, модель, длина/ширина/объём/вес, материал, заметки); `GET /gear/mine`, `GET /gear/:userId` (с проверкой видимости профиля), `POST /gear`, `PATCH/DELETE /gear/:id`. Web: страница `/gear` (CRUD) и блок снаряжения в профиле пользователя. Связь с заплывами — не реализовано.
4. **Новости (§36 п.57, п.59).** Модуль `news`: лента с пагинацией, публикация/черновик (`isPublished`), обложка; создание/редактирование/удаление — только `admin/moderator` (`RolesGuard`). Web: `/news` (лента, для staff — черновики и форма создания), `/news/:id` (статья, публикация/снятие, удаление). Категории и комментарии — не реализовано.
5. **Настройка уведомлений (§26.3).** Таблица `notification_settings` (7 категорий × флаги `inApp`/`push`, значения по умолчанию — включены); `GET /notifications/settings`, `PATCH /notifications/settings/:category`; `notify()` проверяет настройку перед записью in-app и перед отправкой FCM. UI переключателей — в профиле.
6. **Карта водоёма в web.** Компонент `WaterbodyMap` (Leaflet): по имени водоёма ищется OSM-объект (Nominatim), контур подтягивается через Overpass (с зеркалами) и отрисовывается поверх тайлов OSM; используется на странице водоёма.
7. **Прочее по коду.** Глобальный `JwtAuthGuard` (`APP_GUARD`) + `@Public()`; авто-создание чата события при создании заплыва; авто-завершение связанного заплыва при завершении трека; `GET /search` — фильтр блокировок и опциональная JWT (публичный); `PATCH/DELETE /admin/events/:id` (редактирование/удаление событий админом); достижения `social`/`streak_3`; событие `achievements.unlocked` → уведомление + авто-пост; миграция `AuthSecurityHardening` + `migrationsRun`.
8. **Право стаффа править чужие маршруты (§14.4).** `TracksService` вместо проверки «только владелец» использует `ensureEditable()` — владелец или стафф (`admin`/`moderator`): `PATCH /tracks/:id` (название, водоём, сложность), `POST /tracks/:id/points`, `/complete`, `/publish`; `GET /tracks/:id` отдаёт чужой приватный трек стаффу. XP за публикацию и завершение начисляются **автору** трека (`track.userId`), а не тому, кто нажал кнопку. Удаление чужого трека оставлено только администратору (`403` для модератора) — по аналогии с `DELETE /admin/events/:id`. Web: в `/admin/tracks` добавлены кнопка «Править» (модаль: название, водоём, сложность — `PATCH /tracks/:id`), кнопка «Удалить» (только для `admin`) и подсказка о правах. Проверено smoke-тестом `server/scripts/smoke-tracks-staff.js` (15 проверок: 403 у постороннего, 200 у admin/moderator, 403 на удаление у модератора, регрессия прав владельца).
9. **Запуск из корня.** Корневой `package.json` (не workspaces) с агрегирующими скриптами и runner `scripts/dev.js` без сторонних зависимостей: `npm run dev` поднимает backend (`start:watch`) и web (`vite`) в одном терминале с префиксами `[server]`/`[web]`, прокидывает `PORT`/`WEB_PORT`/`VITE_API_PROXY`, останавливает оба процесса при падении одного и по Ctrl+C; если на `PORT` уже отвечает `/api/health` нашего backend — поднимает только web, если порт занят чужим процессом — сообщает об этом и выходит с кодом 1. Есть также `build`, `setup`, `dev:server`, `dev:web`, `start:server`, `smoke:tracks-staff`.
10. **Карта маршрутов (v0.6).** Убран `/admin/tracks` из админ-навигации — управление маршрутами перенесено в `/tracks` («Активность»).
